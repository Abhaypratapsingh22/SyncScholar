## Category A: Numerical Problem-Solving Tests

This is one of the highest-priority testing categories.

Test whether SyncScholar can correctly understand and solve numerical questions from NCERT Class 9 Science.

Cover numerical problems from relevant chapters, including:

- Motion
- Force and Laws of Motion
- Gravitation
- Work and Energy
- Sound
- Atoms and Molecules
- Structure of the Atom
- Other chapters containing mathematical calculations.

### Test different numerical variations:

1. Direct formula-based numerical questions.
2. Multi-step calculations.
3. Questions requiring unit conversion.
4. Questions involving SI units.
5. Questions containing decimal values.
6. Questions involving fractions.
7. Questions involving negative values.
8. Questions requiring rearrangement of formulas.
9. Questions involving multiple scientific quantities.
10. Word problems requiring identification of known and unknown variables.
11. Questions with missing information.
12. Questions containing unnecessary information.
13. Questions with misleading numerical values.
14. Questions involving scientific notation.
15. Questions requiring interpretation of a table or given data.

### Example test cases

**Test 1: Direct numerical**

"A car travels 120 metres in 10 seconds. Calculate its speed."

Expected:
- Identify distance and time.
- Apply speed = distance / time.
- Calculate 12 m/s.
- Provide the correct unit.

**Test 2: Multi-step numerical**

"A body starts from rest and accelerates uniformly at 2 m/s² for 5 seconds. Calculate its final velocity and distance travelled."

Expected:
- Identify initial velocity, acceleration, and time.
- Apply the correct equations of motion.
- Calculate both answers accurately.
- Show the calculation steps.

**Test 3: Unit conversion**

"Convert 72 km/h into metres per second."

Expected: 20 m/s.

**Test 4: Missing information**

"A car travels a certain distance. Calculate its speed."

Expected:
- Identify insufficient information.
- Ask for the missing distance and time.
- Do not invent numerical values.

**Failure conditions:**

- Incorrect formula selection.
- Incorrect substitution.
- Incorrect arithmetic.
- Incorrect unit conversion.
- Incorrect final answer.
- Missing calculation steps.
- Hallucinated values.
- Confidently presenting an incorrect solution.
- Failing to recognize insufficient information.

Record every failure and its exact input and output.

1. Inspect the backend code to identify the Gemini client and API integration.
2. Identify the configured Gemini model.
3. Trace the chatbot request execution path.
4. Determine whether the Gemini API is called when a question is submitted.
5. Inspect API request and response logs, where available.
6. Verify whether the response displayed in the frontend originates from the Gemini API response.
7. Determine whether a hardcoded response, local model, static answer, or fallback mechanism is being used instead.

### Failure conditions

- Gemini API is never called.
- API integration exists but is bypassed.
- Responses are generated from hardcoded content.
- Gemini is called but its response is discarded.
- An incorrect API model or endpoint is configured.
- API authentication fails.
- The backend does not handle API errors correctly.
- The chatbot displays a fallback response without identifying the fallback.
- The frontend displays a response different from the backend-generated response.

**Important:** Do not classify a response as non-Gemini merely because it resembles a textbook answer. Use execution traces, request logs, and code-path verification to establish the actual source.

# 4. FAILURE-ORIENTED TESTING STRATEGY

Do not restrict testing to predefined questions.

Generate additional test questions dynamically based on the following approaches.

### Approach 1: Same concept, different wording

Ask the same question in 5–10 different ways.

### Approach 2: Different difficulty levels

Test easy, moderate, and challenging Class 9-level questions.

### Approach 3: Numerical variations

Change numerical values, units, missing variables, and calculation requirements.

### Approach 4: Conceptual variations

Ask direct, indirect, hypothetical, and application-based questions.

### Approach 5: Boundary testing

Test questions that are just within or outside the expected Class 9 syllabus.

### Approach 6: Adversarial testing

Use misleading wording, unnecessary information, incorrect assumptions, and ambiguous questions.

Do not expect the chatbot to agree with false assumptions.

For example:

"Since sound can travel through a vacuum, why can't we hear sounds in space?"

Expected behaviour: Correct the false assumption and explain that sound requires a material medium.

### Approach 7: Repeated reproducibility testing

Whenever a failure is discovered:

1. Repeat the exact question.
2. Check whether the failure occurs again.
3. Change the wording slightly.
4. Check whether the same failure occurs.
5. Change numerical values if applicable.
6. Determine whether the failure is consistent or intermittent.

Do not count repeated identical failures as separate unique bugs. Group them under one root-cause issue and record the number of occurrences.

### Approach 8: Regression-oriented testing

When one failure is discovered, generate additional questions targeting the same suspected weakness.

For example, if the chatbot fails to convert km/h into m/s, test additional unit-conversion questions from different chapters.

The objective is to discover the full extent of the underlying problem.

# 5. ROOT-CAUSE ANALYSIS

Finding an incorrect response is not sufficient.

For every confirmed failure, investigate WHY the chatbot failed.

Classify the root cause into one or more of the following categories:

| Root-cause category | Examples |
|---|---|
| PDF extraction | Missing or incorrectly extracted content |
| Content structuring | Incorrect chapter or topic classification |
| Chunking | Important concept split across chunks |
| Embedding | Poor semantic representation |
| Vector search | Incorrect or irrelevant retrieval |
| Metadata filtering | Wrong class, subject, or chapter filters |
| RAG augmentation | Retrieved context not included in prompt |
| Prompt engineering | Weak or contradictory instructions |
| Gemini integration | API not called or response mishandled |
| Reasoning | Incorrect conceptual understanding |
| Numerical calculation | Formula or arithmetic error |
| Formula interpretation | Incorrect symbols, units, or equations |
| Conversation memory | Previous context incorrectly retained or lost |
| Frontend | Incorrect response rendering |
| Backend | Request-handling or response-processing error |
| Performance | Excessive latency or timeout |
| Configuration | Incorrect environment or model configuration |

### Root-cause investigation procedure

For every failure:

1. Capture the exact question.
2. Capture the chatbot's complete response.
3. Establish the expected correct response.
4. Identify the failure type.
5. Inspect the backend execution path.
6. Inspect retrieved chunks if RAG is used.
7. Inspect the augmented prompt.
8. Verify Gemini API execution.
9. Identify the earliest stage where the expected behaviour breaks.
10. Determine the most likely root cause.
11. Record supporting evidence.
12. Suggest what should be investigated or fixed later.

If the root cause cannot be conclusively established, label it as **Suspected Root Cause** and explain what additional evidence is required.

Never invent a root cause based only on the final answer.

Every test must contain:

- Test ID.

- Question.

- Expected answer or expected behaviour.

- Test result.
- Failure description.
- Root-cause category.
- Root-cause explanation.
- Supporting evidence.
- Reproducibility status.
- Severity.
- Suggested investigation or fix.

Use the following result classifications:

**PASS:** The chatbot behaves correctly.

**FAIL:** The chatbot produces an incorrect, incomplete, irrelevant, or otherwise unacceptable result.

**PARTIAL PASS:** The answer is mostly correct but has identifiable weaknesses.

**BLOCKED:** The test cannot be completed because of an external dependency or unavailable service.

**INCONCLUSIVE:** Available evidence is insufficient to determine whether the chatbot passed or failed.

Do not mark an unverified test as PASS.

# 7. PRIORITY AND SEVERITY CLASSIFICATION

Classify discovered problems using four severity levels.

**CRITICAL**
- Gemini integration completely broken.
- Chatbot consistently unable to generate responses.
- Major scientific misinformation.
- Wrong class or subject knowledge being served systematically.
- Critical data or API security exposure.

**HIGH**
- Incorrect numerical answers.
- Incorrect scientific formulas.
- Consistent RAG retrieval failures.
- Major conceptual inaccuracies.
- Gemini API responses being incorrectly discarded.

**MEDIUM**
- Incomplete explanations.
- Incorrect or inconsistent examples.
- Poor question interpretation.
- Weak handling of follow-up questions.
- Incorrect formula formatting.

**LOW**
- Minor vocabulary problems.
- Small formatting issues.
- Minor response-structure inconsistencies.
- Unnecessary verbosity.

Prioritize failures based on their actual impact on students, not simply how frequently they occur.
